# Blingiton web

Storefront + admin for Blingiton (925 silver jewelry, Amman). Next.js 16 + Payload CMS 3 in one app, Postgres, English + Arabic (RTL). Replaces the old WooCommerce site. Plan: `C:\Users\LENOVO\.claude\plans\dreamy-sniffing-brooks.md`.

This project uses the Payload CMS skill at `.claude/skills/payload/`. Start with `.claude/skills/payload/SKILL.md`, then `.claude/skills/payload/reference/` for details.

## Commands
- `npm run dev`: app on http://localhost:3000, admin on `/admin`
- `npm run generate:types` after any schema change, then `npm run generate:importmap` if admin components changed
- `npm run typecheck`, `npm run lint`, `npm run test:unit`
- `npm run build`: needs `DATABASE_URL`

## Layout
- `src/collections/`: Orders, Products, Categories, Reviews, Pages, Media, Users. `src/globals/SiteSettings.ts` holds business details and the SEO writing settings.
- `src/fields/`: shared fields. `seo.ts` has the SEO tab, `seoStatus`, the hidden `ai` bookkeeping, and `legacy` (old WooCommerce IDs and URLs). `slug.ts` is the shared EN/AR slug. `label.ts` has `l(en, ar)` for bilingual admin labels.
- `src/access/`: access rules. Published content is public; drafts are staff-only.
- `src/lib/`: `locales.ts` (en/ar), `site.ts` (`serverUrl`, `isProduction`), `slugify.ts`.
- `src/seo/`: SEO rules (`rules.ts`: length limits, Arabic check), allowed facts per product/category (`facts.ts`), and the writer that fills only empty fields and tracks what AI wrote (`apply.ts`).
  - Automatic writer (`writer.ts`): with `ANTHROPIC_API_KEY` set, the `seo-refresh` job (`tasks.ts`, queued after every save) asks Claude (`claude-opus-5-5`) for only the fields that are still empty, in EN + AR. The request includes the main photo, for alt text. Replies are checked against `rules.ts` and SEO titles must be unique; one retry fixes what failed. Everything then goes through `applyProductSeo` / `applyCategorySeo` / `applyPageSeo`. Fully written items make no API call.
  - Prompt: `prompts.ts`, built from Site settings → SEO writing (facts, voice, never say, search phrases).
- Storefront (`src/app/(frontend)/[locale]/`, `src/components/`): a port of the clickable preview in `../preview/`, which is the design reference. Styles are `site.css` (the preview's, unchanged) and `frontend.css` (the preview's per-page styles).
  - `components/preview/draw.ts`: the canvas name/engraving previews, ported from `preview/assets/site.js`
  - Product choices (`src/lib/choices.ts`): a product's `personalization.options` are ordered questions (kind: design / size / chain / sparkle / finish / colour / other), each with choices that can add a price, show a little picture (swatch or chain pattern) and switch the photo. Questions and choices can be conditional ("only when…": a list of choice ids, same question = or, different questions = and). `personalization.variants` set a price, stock count or photo for a combination; the most specific match wins. The site asks in a fixed order by kind (`stepRank`), with the built-in steps (chain length, stone, name, lettering, silver/gold) slotted in. The same module prices the bag and the server's re-pricing, and `placeOrder` refuses incomplete answers and takes stock off products and combinations. Admin condition picker: `components/admin/ChoiceFields.tsx`.
  - Product page: `components/product/ProductForm.tsx` is the step-by-step piece builder (chain-link progress, one question at a time, a price tag at the end); `live.ts` tells the gallery and headline price what was picked.
  - `components/store/`: the bag (kept in the browser's localStorage), drawers, toast and the silver/gold switch; `/bag-items` returns names and prices for it
  - Checkout posts to `/place-order` (`src/lib/orders.ts`), which re-prices everything from the database and creates the order. Never trust prices from the browser.
  - Orders: WooCommerce-style statuses and list (`src/lib/orderOptions.ts`, admin cells in `components/admin/Order*`). Numbers start at 20001, past the old Woo ones.
  - Order emails (`src/lib/orderEmails.ts`): customer on received and on each stage the shop ticked (Site settings → Orders & alerts), shop on received, once each (`emails.*At`; the shipped one is `completedAt`). Every customer email links to their order page. SMTP via `SMTP_*`; without it they print to the server log.
  - Order pipeline (`src/lib/orderStages.ts`, pure and unit-tested): paid → preparing → packed → shipped → delivered, on active orders only (processing / on hold / completed). `resolveStage` keeps stage and status in step: shipped or delivered = completed. The `orderStage` hook rebuilds `stageSince`, `stageHistory` (who and when) and `stuckAt` (= stageSince + the stage's hours from settings; shipped is timed per delivery method) on every save. Changing the hours re-times open orders (`restampStuck`).
  - Stuck orders (`src/lib/stuckOrders.ts`): red in the list (Stage column, "Stuck" tab), on the dashboard (`components/admin/OrderPipeline.tsx`) and in the order's sidebar (`OrderTimeline.tsx`). The hourly `stuck-orders` job emails `orderFlow.alertEmails` (else the shop email), then again every `remindHours` while still stuck.
  - Shop health (`src/lib/health.ts`, rules in `src/lib/healthRules.ts` (pure, unit-tested), wording EN + AR in `healthText.ts`): problems ranked by rough JOD/day at risk, from the shop's own last 28 days of web orders and funnel visits (orders with attribution `admin` aren't web orders). Tiers: emergency (emailed at once, again every 2 h), urgent (emailed once), soon (09:00 Amman summary), fyi (admin only); "fixed" emails follow. Recipients as stuck orders. The `shop-health` job runs every 10 min: re-sends missing confirmation emails (orders ≥ 20001, last 7 days), gathers facts, crawls hourly (`healthProbe.ts`: key pages, categories, info pages, top 15 + 40 rotating products, home-page links, main photos, reported 404s/photos re-checked, exchange rates), then `planAlerts`. Signals recorded as they happen (`healthSignal.ts`, hidden `health-signals` collection, 30 days): `/place-order` crashes and refusals (`OrderError.product` for sold out), failed emails, old-link 404s in `/redirect-lookup`, and browser reports to `/health-report` (`healthReport.ts`: missing pages, our photos failing to load (`HealthWatch` in the layout), checkouts that never reached the server). State in the hidden `health-state` global. Admin: `/admin/shop-health` (live; "Check now" = POST `/api/globals/health-state/check`, no emails) and the emergency banner/strip on the admin home (last run). `GET /health` is for an outside uptime monitor: 503 on database down, checks not running (production) or an emergency. `scripts/health-check.ts` runs it by hand without emailing (needs `npm run dev`).
  - Admin quick actions (`OrderActions.tsx`): Confirm (pending / on hold), then one stage forward, plus a WhatsApp button with a prefilled update in the customer's language (`whatsappUpdate` in `src/lib/orderTrack.ts`).
  - Customer's order page: `/[locale]/order-status?o=<id>&t=<signature>` (`src/lib/orderTrack.ts`, signed like the review link with a different prefix), noindex. Also linked from the checkout thank-you screen.
  - Returns & refunds (`src/collections/OrderCases.ts`, options in `src/lib/orderCases.ts`): cancellation / return / exchange / refund with reason, whose side, pieces and money back; listed on the order (join field). A finished cancellation cancels the order; a finished refund of the whole total marks it refunded. Stock is not put back automatically.
  - Reviews: the "on its way" email links to `/[locale]/review?o=<order id>&t=<signature>`. The signature and the submission checks live in `src/lib/reviewCheck.ts`; loading and saving is in `src/lib/reviews.ts`. `/submit-review` saves reviews unapproved, marked verified purchase, one per product per order, and emails the shop. Only approved reviews are public and feed the stars and JSON-LD.
  - Origin (direct / organic / referral / utm) is recorded per browser tab in sessionStorage (`src/lib/origin.ts`) and sent with the order.
  - Shop funnel: `track()` (`src/lib/track.ts`) sends visit / view / personalize / add / checkout / whatsapp steps once per visit and product. `/track` stores them in the hidden `events` collection; bots and signed-in staff are skipped. `components/admin/Funnel.tsx` reports the last 30 days on the admin home with SQL aggregates, and takes orders and revenue from the orders' own attribution.
  - Jordan pays card or cash on delivery. International orders pay by card online (HyperPay); without `HYPERPAY_*` settings they fall back to "on hold", arranged on WhatsApp.
  - Card payments (`src/lib/hyperpay.ts`: API calls and pure helpers, unit-tested; `src/lib/payments.ts`: the order side). `placeOrder` saves the order as **pending** (`card_online`), takes the stock and records it in the hidden `stockHeld`, then the checkout sends the customer to `/[locale]/pay/<order id>/<track token>` (the token is `trackToken`). That page's `PayCard` calls `/payment/start` for a HyperPay checkout (order total in JOD, `merchantTransactionId` = `payment.reference`, "<number>-<random>", one per order for every attempt) and loads HyperPay's widget with its integrity hash and `paymentTarget: '_top'`. HyperPay returns the customer to the same page with `?id=<checkout>`; the page asks HyperPay how it went (`verifyCheckout`) and shows the thank-you screen, the decline message with a fresh form, or "confirming…". Paid only on HyperPay's word, by three routes into `settlePayment`: the return page, `/payment/webhook` (AES-GCM, `HYPERPAY_WEBHOOK_KEY`; 503 without it) and the `payment-check` job every 5 min (`paymentsFor(reference)`, for customers who closed the tab). One SQL update claims `payment.paidAt`, so only one route moves the order to processing (the received emails then go out through the Orders hooks). A payment that arrives after an order was cancelled reopens it with a note; amount mismatches and HyperPay "review" codes add a ⚠ note. Unpaid an hour after the last attempt (`payment.checkoutAt`), the job cancels the order and puts `stockHeld` back. Never emails for pending orders. The bag is kept until the payment goes through (`rememberPaying` / `PaidThanks` in `components/checkout/Thanks.tsx`). Test cards are in HyperPay's onboarding email; the test server only approves whole amounts.
  - Shipping (`src/lib/shipping.ts`): Jordan = Amman / other cities. Abroad = DHL Express (3–5 business days) or standard shipping (14–20), priced by zone (Middle East & Gulf / Europe / US; every other country pays the US price). The country list and its zones live there; fees are in Site settings → Delivery & returns. A bag with any made-to-order piece shows "made in 3–5 days, then …". Carrier war/emergency surcharges are the customer's (checkout note).
  - Gift card: an optional paid card at the end of checkout with the customer's message (`giftMessage` / `giftCardFee` on the order; price in Site settings). It replaced the per-piece "this is a gift" toggle on the product page.
  - Two-factor login (`src/lib/twoFactor.ts`, `src/lib/totp.ts`): required for every admin account. `holdForTwoFactor` (afterLogin) moves the new Payload session out of `user.sessions` into the hidden `two-factor` collection, so the cookie authenticates nothing until `/api/users/two-factor` checks the code and puts it back. The code step renders on the login page (`components/admin/TwoFactor.tsx`, a `beforeLogin` component that hides the password form). First login shows a QR to set up an app and 10 one-time recovery codes; a recovery code leads straight to setting up a new phone. Secrets are AES-GCM sealed with a key from `PAYLOAD_SECRET`. Limits: 5 wrong codes per login, 10 per account per hour. `auth.useSessions` must stay on. "Trust this browser" (ticked by default) sets an httpOnly `<prefix>-trust-<userId>` cookie (path `/api/users`, 30 days; only its hash is stored in `trusted`), and `holdForTwoFactor` lets that browser's logins keep their session with just the password. Password resets always ask for the code. A recovery code, a password change (`forgetTrustedOnPasswordChange`), a reset, or `admin-recovery.ts` (RESET_2FA / NEW_PASSWORD / LOGOUT) forgets every trusted browser.
  - Security alerts (`src/lib/loginAlerts.ts`): failed logins, lockouts (5 tries → 15 min), password-reset requests, wrong 2FA codes, recovery codes used, 2FA set up, logins from a new country (or IP), and team changes (new account, made admin, email changed, deleted) email `SECURITY_ALERT_EMAILS` (else every admin) with the IP, location from Cloudflare/Vercel headers and browser. Throttled per IP, except the rare important kinds.
  - Audit log (`src/lib/audit.ts`, collection `audit-log`, admin → Team): auth events plus every create/update/delete by a signed-in person (added to all collections and globals by the last plugin in `payload.config.ts`). Read-only for admins, no API writes. Entries are HMAC-chained; `scripts/audit-verify.ts` finds edited or removed entries.
  - Customers (`src/collections/Customers.ts`, rules in `src/lib/customerStats.ts`, server side in `src/lib/customers.ts`): every order is linked to a customer (`customerRecord`) by email, else by phone (normalised to `9627…`), never onto a customer with a different email. Totals, dates, segment (one-time / returning / loyal) and favourite category are recounted from their orders after each order save. Purchases = processing / on hold / completed; *verified* = completed. Staff read and add notes; only admins export (`GET /api/customers/export`, CSV with the list's filter, audited) or delete. `scripts/customers-backfill.ts` links old orders.
  - Customer insights: `/admin/customer-insights` (`components/admin/CustomerInsights.tsx`, data in `src/lib/insights.ts`, personas in `src/lib/personas.ts` = segment × Jordan/abroad, counted only from orders) and each customer's Insights tab (`CustomerView.tsx`).
  - Browsing of returning customers (`src/lib/activity.ts`, collection `customer-activity`): only when the customer ticked "Remember me on this device" at checkout (unticked by default; consent stored on the customer with time and wording version), the browser holds the signed `bl-cust` cookie (`src/lib/customerToken.ts`), and they have a completed order. Records views, active time (`src/lib/customerTrack.ts`), picked options and adds, never the engraved name. `/[locale]/your-data` lets them stop and erase on every device (epoch bump); admins can do the same from the Insights tab. The nightly `prune-activity` job deletes rows after 365 days (needs `JOBS_AUTORUN`, or a scheduler calling `/api/payload-jobs/handle-schedules` and `/run`). Interest is reported as interest, never as purchase intent.
  - Currency (`src/lib/currency.ts`): prices are stored, ordered and charged in JOD, but shown in the visitor's currency. The proxy sets the `bl-currency` cookie from `cf-ipcountry` / `x-vercel-ip-country` on the first visit (no header → JOD; crawlers are skipped), and the header dropdown (`CurrencyPicker`, flags in `public/flags/` from flag-icons, MIT) changes it. Rates come from `src/lib/rates.ts` (daily, fixed fallback). Show prices with `<Price jod>` / `useMoney()` from `components/store/Money.tsx`, never `money()`, which is JOD-only for emails and llms.txt. Page HTML, JSON-LD and the Google feed stay in JOD; `data-price` elements are hidden until converted, so there's no JOD flash.
  - Gift finder (`/[locale]/finder`, engine in `src/lib/finder.ts` (pure, unit-tested), catalog in `src/lib/finderData.ts`): five questions (for whom, occasion, budget, style, finish), each answer a link (`?for=&occasion=&budget=min-max&style=&finish=`), then 3–5 picks with reasons. Rule-based. Each product has a "Gift finder" tab (`finder`: forWhom / occasions / styles, plus `checked` for the shop and a read-only `suggested` mark); when tagged, those win. Untagged products (e.g. new ones) are matched on guesses from categories, kind, personalisation, gold, stones and EN/AR words in name / short description / search phrases (`themesOf`). Price, stock and 180-day sales always count. Products in no category (gift vouchers, the gift card) are never picked. Budgets are quarters of live prices. Never picks sold-out or 0 JOD pieces; when few match the style or budget it says so (`fewExact`, `stretched`, `fewGold`). Results reuse `ProductCard` (quick add or "Personalise"). Home section + "Gift finder" in the top menu. Only the bare page is indexed. Funnel events `finder` / `finder-done` (path keeps the answers) / `finder-click`; clicking a pick sets sessionStorage `bl-finder`, and the order gets `attribution.finder`. Admin home: `components/admin/FinderStats.tsx` (usage, plus "tags checked on X of Y products" with a link to the unchecked ones).
  - Back in stock (rules in `src/lib/restock.ts`, pure and unit-tested; server side `src/lib/restockNotify.ts`; collection `restock-requests`, admin → Shop): a sold-out piece or combination shows "Email me when it's back" (`components/product/NotifyMe.tsx`, a `div`, not a `form`: it sits inside the builder's form) unless the piece is one-off. `/restock-request` takes the product + answers; the server works out what's empty with the same `resolve` as checkout (a combination with its own count of 0 → a `variant` request, else the whole piece) and saves one waiting request per product + combination + email. `restockAfterChange` (Products) emails, after the response, everyone whose piece `isBack` (live, priced, not sold out, stock > 0 when counted, the combination's own count > 0); the hourly `restock-notify` job is the safety net and prunes (emails cleared 90 days after use, waits expire after a year). Requests are claimed with a single SQL update (waiting → notified) before the email, so concurrent runs can't double-send; a failed send puts them back and records a health signal. One email per person and piece, in their language, with the photo of what they picked and a `utm_source=restock` link. `src/lib/restockTask.ts` imports the notifier lazily (it reads `data.ts`, which imports the config). Admin home: "Most wanted back" (`components/admin/RestockDemand.tsx`).

## SEO score (admin)
- `src/seo/score.ts` scores a product 0–100 from the same rules as the pipeline, plus photos, approved reviews and price. It is stored in `seoScore` so the list can sort and filter by it.
- The pipeline (`applyProductSeo`) stores the score on every save, and review hooks refresh it. `storeScores` writes the products table and the latest row of `_products_v`, because the admin list reads versions (products have drafts). A plain `payload.db.updateOne` would leave the list showing stale scores.
- Admin UI pieces live in `src/components/admin/`: the dashboard (`beforeDashboard`), score panel (the `seoScore` field), list cells, and logo. Styles are in `src/app/(payload)/custom.scss`. Run `npx payload generate:importmap` after adding a component path.

## Rules
- **Host-neutral.** Hosting is undecided (Hetzner/Coolify, Vercel, DigitalOcean). Avoid host-specific APIs:
  - storage goes through `@payloadcms/storage-s3`
  - jobs go through the Payload queue (`JOBS_AUTORUN` or `/api/payload-jobs/run` + `CRON_SECRET`)
  - indexing is gated by `SITE_ENV`
- **Only `SITE_ENV=production` may be indexed.** Everything else gets noindex.
- **Every user-facing string exists in EN and AR.** Admin labels use `l()`. Content fields are `localized: true`.
- **The SEO pipeline only fills empty fields.** Never overwrite text a person wrote.
- **AI text states facts from the product or from SiteSettings → SEO writing → facts only.** No invented claims.
- **Scripts run outside the server, so their saves don't clear its page cache.** After running one against the database, restart `npm run dev` and delete `.next/dev/cache/fetch-cache`. When an `unstable_cache` function's query changes, bump its key (e.g. `'v2'`).
- **Pass `req` to nested Payload operations in hooks**, and guard re-saves with `context` flags. See the Payload skill's security notes.
